View 1 - FBV: Manual HttpResponse
-------------------------------------------------

View Name: course_summary_view
Purpose: Displays a summary of Course objects.

The view queries the Course model, manually loads the template, manually renders the template, and wraps the result in HttpResponse.

URL: /courses/summary/


View 2 - FBV: render()
------------------------------------------------

View Name: course_list_view
Purpose: Displays a list of Course objects.

The view queries Course.objects.all() and passes the data to
the Course list template using render().

URL: /courses/


View 3 - Base CBV
------------------------------

View Name: CourseOverviewView
Purpose: Displays an overview of Course objects.

The class inherits directly from django.views.View and implements
get() to query the Course model and render a Course template.

URL: /courses/overview/


View 4 - Generic Class-Based View
---------------------------------

View Name: CourseDetailView
Purpose: Displays one individual Course.

The class inherits from Django's DetailView.

It specifies:

- model = Course
- template_name = "courses/course_detail.html"
- context_object_name = "course"

We used the primary key provided in the URL to retrieve the
correct Course object.

URL: /courses/<course_id>/

VIEW REFLECTION

HttpResponse vs render()
------------------------

The manual HttpResponse approach was useful for understanding what
Django is doing because the view explicitly queries the model, loads the template
, creates the context, renders the template, and then wraps the rendered HTML in HttpResponse.

This made the entire process easier to understand.

The render() shortcut was more convenient for some
pages because it combines template loading and
returning the HttpResponse into a simpler function call.

We decided that for most pages, render() would be easier to read
and maintain.


Base CBV vs Generic CBV
-----------------------

The base View class was useful when we wanted more direct control over
what happens during a request.

For CourseOverviewView, we manually implemented get() and queried the
Course model and then selected the template.

A generic CBV such as DetailView was useful for a common Django pattern.

For CourseDetailView, Django already knows how to retrieve one Course
using its primary key, so we only needed to specify the model,
template, and context object name.

We liked generic CBVs because they reduced repeated boilerplate code, while the
base View class seems more useful when custom request-handling logic is needed.

Section 1: URL Linking & Navigation
get_absolute_url() is implemented on the Course model. It's useful because both the
dashboard and the course list page need to link to a course's detail page (/courses/<pk>/).
Without it, we'd have to manually build that URL string in every template that links to a course.
Instead, both templates just call {{ course.get_absolute_url }}, and if the detail URL pattern ever changes,
we only update it in one place (models.py) instead of every template.

Section 3 : Static files & UI Styling
We chose to put all the static files inside the same folder, as we thought it would
make calling the css files more simple and to avoid having to call files with increasingly
long pathnames. We used normalize to make it so that the UI would not end up breaking or malfunctioning
in different browsers, and used a framework of skeleton to define a few components that we thought
would be used many times. Style was used to actually make the overall UI look different, usig {% load static %}
to apply the style file on the corresponding html files.

Section 6: Creating APIs

HttpResponse vs JsonResponse: HttpResponse is a general response and it can be used for HTML,
images, and more. We used HttpResponse for the Matplotlib chart endpoint with the MIME type image/png.
JsonResponse is used for structured JSON data and automatically sets the
response content type to application/json. We used JsonResponse for the course API.

For ClassCompass, we will create more APIs that expose important project data
in JSON format so that the frontend or other applications can access the data
without relying on the HTML pages.

We currently have a Course API that returns course information from the database and allows for filtering.
We plan to create additional API endpoints for other ClassCompass features, including the Courses, Academic
events and deadlines, Grades, Syllabi and syllabus processing information, and Study tools.

The type of data served will depend on the feature. Course APIs
will return course code, course name, term, and year. Academic event APIs will
return event titles, event types, dates, estimated workload, and completion
status. Grade APIs will return assignment or exam information and points or
weights. Study tool APIs will return generated study guides, summaries, or
practice-question information.

The current implemented endpoint is:
/api/courses/
Example filtered request:
/api/courses/?q=CS

Assignment 6 – Part 3: Production Reflection

QUESTION 1
The Size vs. Quality Trade-off: Based on our testing of 15 Hugging Face models, the 3B–7B parameter category
provided the best balance between performance and computational requirements for ClassCompass. Our application
focuses on extracting assignment names, deadlines, and estimated workload from syllabus text, so we prioritize
accurate and consistently formatted JSON outputs. Qwen3-4B-Instruct achieved 100% field accuracy and 100% strict
JSON compliance, matching the performance of larger models such as Qwen2.5-14B-Instruct. This showed that a much
larger model was not necessarily better for our specific task. Some other 14B models achieved 100% field accuracy
but failed to return strictly formatted JSON.

Estimated computational requirements and hosting costs:

Model size       | Approx. memory for weights (FP16) | Estimated monthly GPU hosting cost
-----------------|-----------------------------------|-----------------------------------
Under 1B         | Under 2 GB                        | $50-$150
1B-3B            | 2-6 GB                            | $100-$300
3B-7B            | 6-14 GB                           | $200-$600
7B-13B           | 14-26 GB                          | $400-$900
13B+ (14B tested)| Around 28 GB                      | $700-$1,500+

These are rough illustrative monthly estimates, not measured cloud prices. They assume an appropriate server
configuration and usage-dependent hosting, rather than a continuously running dedicated GPU. Actual costs depend
on hardware, quantization, traffic, and provider pricing.

Conclusion: We would choose Qwen3-4B for ClassCompass because it achieved the same accuracy and JSON reliability
as our best larger models while requiring substantially less memory and computation. This makes it a more practical
option for local deployment, subject to available server resources.

QUESTION 2
Cost & Scaling: So for our app, Hugging Face models are used for syllabus-information extraction.
If ClassCompass scaled to 10,000 users, the app would need to handle way more AI requests, including simultaneous syllabus uploads.

Assumptions

Daily active users: 10,000
AI requests per user per day: 2
Average input tokens per request: 1,000
Average output tokens per request: 200
Monthly AI requests: 600,000
Monthly input tokens: 600 million
Monthly output tokens: 120 million

These are just assumptions, but the actual cost would depend on how often students use the AI features.
The number of monthly requests is: 10,000 users × 2 requests/day × 30 days = 600,000 requests/month
The monthly token usage is:
- Input: 600,000 × 1,000 = 600,000,000 tokens
- Output: 600,000 × 200 = 120,000,000 tokens

Running a Local Model:
For local deployment, Django would use the transformers library to run a pretrained model
on a GPU-equipped server such as an AWS EC2 instance. This gives us greater control over the model, keeps student
syllabus data private, and eliminates per-token API fees. However, we would still need to cover GPU computing,
storage, and server maintenance costs, even when usage is low. Running a AWS EC2 instance continuously
would cost probably $1200 per month, with maybe an additional $100 for 1,000 GB of storage. This brings the estimated
monthly cost to ~ $1300, excluding additional expenses such as database hosting, networking, maintenance, etc.
This estimate assumes one GPU server can handle all 600,000 monthly requests, but demand could spike to more.

Using a paid external API:
With an API, ClassCompass would send requests to an external provider. We calcualted these costs based on the number of
input and output tokens processed, and pricing varies across providers and models. Here is a pricing comparison:

API Model               Input / 1M Tokens   Output / 1M Tokens
GPT-6 Luna (standard)   $0.10               $0.50
GPT-5 Mini              $0.25               $2.00
GPT-6 Sol (standard)    $2.00               $10.00

ESTIMATED MONTHLY API COSTS BY NUMBER OF USERS

Daily Users | Monthly AI Requests | GPT-6 Luna | GPT-5 Mini | GPT-6 Sol
------------|---------------------|------------|------------|----------
100         | 6,000               | $1.20      | $3.90      | $24
1,000       | 60,000              | $12        | $39        | $240

For GPT-5 Mini, the calculation is:
Input cost = 600 × $0.25 = $150
Output cost = 120 × $2.00 = $240
Total monthly API cost = $390

For an increase to 10,000 daily users, we would choose using an external API
as the primary service, but have the local model as a possible component of a hybrid system. This is because
a low-cost API could be less expensive than operating even one dedicated GPU server continuously, and an API provider
reduces the need to maintain GPU infrastructure, scaling, etc.

QUESTION 3
Hybrid Potential: Instead of relying entirely on a local model or a paid API, we could use a hybrid approach for ClassCompass.
Our local Hugging Face model would handle simpler tasks, like extracting assignments, deadlines, and workload estimates from
uploaded syllabi. We would then validate the results before adding them to the student's calendar, checking that the output
is valid JSON, includes all required fields, and contains information supported by the original syllabus. If the local model
produces invalid output, misses important deadlines, or struggles with ambiguous information, we could send
the relevant text to an external API for a second attempt.

This approach would help us minimize costs because most routine requests would be handled locally, and we would only pay for
API usage when necessary. We could also compare the results of both models during testing to determine when API fallback
actually improves accuracy. This would allow us to balance cost, and reliability as our app grows.

QUESTION 4
Cost Comparison: Hosting a pre-trained model ourselves would require paying for a server, even when the application has few
users. A paid API, on the other hand, generally charges based on the number of input and output tokens processed.

For our comparison, we considered an AWS EC2 g5.4xlarge server with 16 vCPUs, one NVIDIA A10G GPU, 64 GiB RAM, and 1
TB of storage. Based on our earlier calculations, this would cost approximately $1300 per month.

Expense          | Local Pre-trained Model                                  | Paid API
-----------------|----------------------------------------------------------|-----------------------------------------
Initial setup    | Requires configuring the server and model                | Simple integration
Monthly cost     | Approximately $1300 for one continuously running         | Depends on token usage and model pricing
                 | GPU-enabled server                                       |
Cost per request | No separate API charge; server costs are shared          | Charged based on input/output tokens
                 | across requests                                          |
Scaling          | May require additional servers as usage increases        | Provider handles much of the scaling
Maintenance      | We manage model updates, errors, and performance         | Provider manages model infrastructure
Data privacy     | More direct control over how data is processed           | Data is sent to an external provider


For ClassCompass, local hosting would be a good option if we had consistently high usage and our Hugging Face model
performed accurately. However, we would also be responsible for server maintenance and ensuring that our GPU could
handle the number of requests.

A paid API would be better if we had fewer users or unpredictable traffic, especially since syllabus uploads might
increase significantly at the beginning of each semester. For 10,000 daily users making two requests each, we would
process approximately 600,000 requests monthly.

These API costs are hypothetical and depend on token usage and model pricing. We would also need to compare models
